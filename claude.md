## Project overview

BorrowCircle is a campus-only web platform where verified KNUST students can list
items they own (calculators, textbooks, lab coats, cameras, etc.) and let other
students borrow or rent them for a short period. Full product spec, feature list,
database design, and sprint plan live in `/docs/BorrowCircle_MVP_v2.md` — treat
that file as the source of truth for scope and acceptance criteria. If a task
conflicts with that document, stop and ask rather than guessing.

MVP duration: 4 weeks / 4 sprints. We are building sprint by sprint, feature by
feature. Do not build ahead of the feature currently requested, even if you can
see later features in the spec — implementing out of order creates merge
conflicts and untested code paths.

## Tech stack

- **Backend:** Node.js + Express + TypeScript
- **Frontend:** React + TypeScript + Vite + Tailwind CSS
- **Database:** PostgreSQL (local dev via Docker Compose)
- **ORM:** Drizzle ORM + drizzle-kit for migrations
- **Package manager:** npm, using npm workspaces (`client/`, `server/`)
- **Testing:** Jest (or Vitest) + Supertest for backend integration tests
- **Linting/formatting:** ESLint + Prettier

## Commands

```bash
# Start local database
docker compose up -d

# Backend (from server/)
npm run dev              # start dev server with hot reload
npm run build             # compile TypeScript
npm run lint               # run ESLint
npm run test                # run full test suite
npm run test:watch           # run tests in watch mode
npm run db:generate           # generate a new Drizzle migration from schema changes
npm run db:migrate             # apply pending migrations
npm run db:studio               # open Drizzle Studio to inspect data
npm run test:db:reset            # drop and re-migrate the test database

# Frontend (from client/)
npm run dev              # start Vite dev server
npm run build             # production build
npm run lint               # run ESLint
```

Always run `npm run lint` and `npm run test` before considering a feature done.
Prefer running a single test file while iterating (`npm run test -- auth.test.ts`)
rather than the whole suite, for speed — but run the full suite before declaring
the feature complete.

```
  docs/
    BorrowCircle_MVP_v2.md   full product spec — source of truth for scope
  CLAUDE.md
```

Follow this structure for anything new. Business logic belongs in `services/`, not
in controllers or route handlers — controllers should stay thin (parse request,
call a service, shape the response).

## Code style

- TypeScript strict mode is on (`strict: true`) — do not weaken it to make an
  error go away; fix the underlying type issue.
- Use ES modules (`import`/`export`), not CommonJS (`require`).
- Prefer named exports over default exports, except for React components.
- Validate all request bodies with `zod` schemas and the shared validation
  middleware — do not hand-roll validation in a controller.
- Never write raw SQL strings for queries covered by Drizzle — use the query
  builder so types stay accurate. Raw SQL is only acceptable for migrations or
  genuinely unsupported query shapes, and should be commented explaining why.
- Environment variables are read only in `config/`, never accessed via
  `process.env` scattered through the codebase.
- Every enum used in the database (item status, request status, roles, etc.)
  must match `docs/BorrowCircle_MVP_v2.md` exactly — do not invent new status
  values without updating the doc first.

## Testing requirements (applies to every feature, no exceptions)

**Every backend feature must ship with automated tests before it is considered
done — not "tests can come later."** This includes:

- **Unit tests** for service-layer logic (business rules, calculations, token
  handling, validation logic) in isolation from the database and HTTP layer.
- **Integration tests** (Supertest against the real Express app + a dedicated
  test database) for every new or changed endpoint, covering:
  - The happy path.
  - Every rejection/failure case listed in that feature's acceptance criteria
    in `docs/BorrowCircle_MVP_v2.md` (e.g. duplicate email, unauthorized access,
    invalid state transitions, expired tokens).
  - Authorization checks — confirm a user cannot act on data they don't own
    (e.g. only an item's owner can cancel it; only the borrower can cancel
    their own request).
- Tests run against a **separate test database**, never the dev or prod
  database. Reset it with `npm run test:db:reset` before the suite runs.
- Before telling me a feature is complete, run the full test suite and show
  me the output (pass/fail summary), not just a claim that it passes.
- If you change existing behavior, update or add tests for it in the same
  pass — do not leave the test suite out of sync with the code.
- If a bug is found later, write a failing test that reproduces it first,
  then fix the code until that test passes.

## Git and commit workflow — IMPORTANT

**Never run `git add`, `git commit`, `git push`, or open a pull request
yourself.** This applies even if I ask you to "commit" casually — confirm with
me first, and even then, do not run the commit yourself.

Instead, when a feature or change is complete and tests pass:
1. Show me a summary of what changed and why.
2. Give me the exact `git` command(s) to run — the `git add` and `git commit`
   with a descriptive commit message already written out for me to copy — so I
   can review and run them myself. Keep commit messages short and brief (a
   single concise summary line — avoid long multi-paragraph messages).
3. Do not stage files (`git add`) on my behalf either.

**Merging is allowed, with conditions.** Unlike commits, you may run `git merge`
yourself — for example, merging a completed feature branch back into `develop`
— but only when:
- The branch being merged in has passing tests and lint, verified by you in
  the same session.
- I have explicitly told you to go ahead and merge (don't merge proactively
  just because a feature looks done).
- You are not merging into `main`/`production` — merges into `main` still
  require me to do it myself, the same as a commit.
- If a merge produces conflicts you can't resolve confidently, stop and show
  me the conflicting files rather than guessing at a resolution.

You may run read-only git commands freely (`git status`, `git diff`,
`git log`, `git blame`) to understand the current state of the repo.

## Workflow rules

- **Stay in scope.** Build only the feature explicitly requested in the current
  prompt. If you notice something in a later sprint that this feature depends
  on, flag it to me instead of building it preemptively.
- **Explore, then plan, then implement** for anything non-trivial (more than a
  one-file change, or anything touching the database schema, auth, or a status
  state machine). Tell me your plan before writing code if the approach isn't
  obvious.
- **Verify your own work.** After implementing, run lint and the full test
  suite yourself and fix failures before telling me it's done. Show me the
  actual command output as evidence, not just "tests pass."
- **Never commit secrets.** `.env` files, API keys, and database credentials
  must never be written into a file that gets committed. Use `.env.example`
  with placeholder values for anything that needs documenting.
- **Migrations are additive.** Do not edit a migration that has already been
  applied and committed — generate a new one. If you need to change a table
  that already has a migration, create a new migration file.
- **Ask before large refactors.** If fixing something requires touching more
  than a couple of unrelated files, tell me what you plan to change and why
  before doing it.
- **Flag ambiguity instead of guessing** on anything affecting money, data
  integrity, or security (e.g. what happens to a pending request when an item
  is cancelled) — check `docs/BorrowCircle_MVP_v2.md` first, and if it's still
  unclear, ask me.

## Definition of done

A feature is not done until:
- It works according to the acceptance criteria in `docs/BorrowCircle_MVP_v2.md`.
- Input validation is in place for every endpoint touched.
- Errors are handled clearly and don't leak internal details (stack traces,
  raw DB errors) in API responses.
- Unit and integration tests exist and pass (see Testing requirements above).
- The code has been linted with no errors.
- Nothing outside the current feature's scope was changed.
- I have been given the exact git command to review and run myself.

## Common gotchas / project-specific notes

- Email domain restriction for registration is controlled by the
  `ALLOWED_EMAIL_DOMAINS` env var — never hardcode the university domain in code.
- Passwords, refresh tokens, and password-reset tokens are always hashed before
  storage. Never log a raw password, token, or reset link in production code
  paths (console logging a reset link is only acceptable behind a development-
  only branch, as set up in the Auth feature).
- Item and request status values are fixed enums defined in
  `docs/BorrowCircle_MVP_v2.md` — do not add ad hoc status strings.
- Accepting a borrow request must be an atomic operation (only one request can
  be accepted per item at a time) — watch for race conditions here.
- The `client/` and `server/` workspaces are independent — don't import server
  code into the client or vice versa. Shared types, if ever needed, should go
  in a dedicated shared package, not a cross-import.
